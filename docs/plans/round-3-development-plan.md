# 第三部分：Round 3 必须交付的开发目标

本轮至少包含六个实质功能模块。前四项为重点交付，后两项用于提升完整度。

## 功能一：多来源英文文章自动发现与本地阅读系统（P1，核心新功能）

### 3.1 产品目标

用户打开词光后，不再只能看到 RFC，而是可以看到真实英文新闻、杂志、科学和文化文章。

首批来源至少纳入正常内容发现体系：

- BBC News
- Reuters
- AP News
- The Guardian
- NPR
- Deutsche Welle（DW）
- VOA Learning English
- NASA
- Wikipedia / Wikinews

不要求所有来源使用同一种获取方法。所有来源都应能进入正常发现列表；能够通过相应方式取得全文的来源进入原生阅读器，其他来源保留标题、摘要和原站阅读入口。

**至少接入 5 个真实来源的自动发现；至少 2 个来源完成真实正文获取、结构化解析和本地持久化完整链路。**

### 3.1.1 来源接入方式

优先级：

1. 官方 RSS / Atom。
2. 官方 API。
3. 来源允许的结构化页面数据。
4. 允许的 HTML 正文提取。
5. 只能取得元数据的来源提供原站阅读模式。

第一批示例：

- BBC Top Stories：https://feeds.bbci.co.uk/news/rss.xml
- BBC World：https://feeds.bbci.co.uk/news/world/rss.xml
- BBC Technology：https://feeds.bbci.co.uk/news/technology/rss.xml
- DW Top Stories：https://rss.dw.com/rdf/rss-en-top
- DW All English：https://rss.dw.com/rdf/rss-en-all
- VOA Learning English：https://learningenglish.voanews.com/rssfeeds
- Guardian API：https://open-platform.theguardian.com/documentation/
- NASA API：https://api.nasa.gov/
- Wikimedia REST：https://www.mediawiki.org/wiki/API:REST_API

开发时必须真实验证 Feed/API 的状态和返回结构。不能把第三方 RSS 目录当作官方端点。

Reuters 和 AP 是重要主流来源，优先使用可用的官方内容入口或授权 API；没有全文接口权限时仍应出现在发现列表，但不应伪装成完整正文。

### 3.1.2 技术架构

建立或扩展：

- ArticleSourceRegistry
- ArticleDiscoveryService
- RSSParser
- OfficialAPIAdapter
- ArticleFetchService
- ArticleHTMLExtractor
- ArticleDocumentNormalizer
- ArticleQualityValidator
- ArticleRepository
- ArticleRecommendationService

优先复用现有 ContentRepository、ArticleCandidateProvider、LearningServices，不得重复建立第二套每日任务状态机。

来源配置至少包含 sourceID、sourceName、websiteURL、feedURLs/apiEndpoint、category、discoveryMethod、contentMethod、refreshInterval、fullTextStorageAllowed、lastSyncAt、ETag/Last-Modified、lastError、enabled。

### 3.1.3 自动发现和下载

必须实现：

- App 启动时按需刷新。
- 今日/探索页面进入时检查来源缓存新鲜度。
- 用户手动刷新。
- iOS 后台刷新作为尽力而为能力，不依赖固定时间执行。
- RSS/Atom XML 解析。
- API JSON 解析。
- canonical URL 规范化。
- 新文章入库。
- 标题、作者、时间、摘要、来源和分类提取。
- 正文获取与发现分离。
- HTTP 304、ETag、Last-Modified。
- 超时、限流、断网、错误状态和重试。
- 有上限的并发和指数退避。
- 一个来源失败不能导致其他来源失败。

### 3.1.4 正文提取

对可取得完整正文的来源：

1. 优先 API 结构化正文。
2. 再解析 Feed 正文。
3. 再解析 JSON-LD 的 NewsArticle/articleBody。
4. 再解析 HTML 的 article/main/p/h1/h2/blockquote/ul/ol。
5. 必要时使用 Readability 思路的正文提取器或 SwiftSoup。

过滤导航、广告、Cookie、推荐卡片、评论区、订阅引导和重复模块。

保留正文标题、小标题、引用、列表、图片说明和有意义的链接。

不得将登录页、验证码页、403/429 错误页或空白页面当成文章正文。

### 3.1.5 本地数据库

继续使用 SwiftData。保存 articleID、sourceID、canonicalURL、title、author、publishedAt、fetchedAt、summary、rawContent（适用时）、structuredBody、bodyHash、wordCount、estimatedReadMinutes、topicTags、contentStatus、extractionVersion、lastError。

完整正文可保存时，重启后仍可离线阅读。元数据/摘要模式不能标记为 fullText。缓存清理不能删除阅读进度、生词本和复习记录。

### 3.1.6 去重

至少包括：

- canonical URL 去重。
- 正文 SHA-256 指纹。
- 标题相似度。
- 同一事件近似重复报道。

不能每天给用户推荐同一篇文章或同一事件的轻微改写版本。

### 3.1.7 文章库与探索 UI

### 3.1.8 每日学习整合

## 功能二：多来源英语词典聚合系统（P1，核心新功能）

### 3.2.1 目标

从单一 CC-CEDICT 反向索引升级为真正的英语词典系统。

至少接入两个真实数据来源，并保留现有 CC-CEDICT。

优先考虑：

- Wiktionary / MediaWiki API
- Free Dictionary API
- Open English WordNet
- 现有 CC-CEDICT
- Merriam-Webster API（配置和使用条件满足时）

### 3.2.2 技术架构

建立：

- DictionaryProvider protocol
- DictionaryAggregator
- LocalDictionaryProvider
- WiktionaryProvider
- FreeDictionaryProvider
- OpenEnglishWordNetProvider
- CCEDICTProvider
- DictionaryCacheRepository

不要将所有请求写在 View 中。

### 3.2.3 词条数据

至少支持 lemma、surface form、IPA、pronunciation、part of speech、English definition、Chinese translation、examples、usage labels、phrases、synonyms、antonyms、word forms、sourceID、confidence、sourceVersion、fetchedAt。

### 3.2.4 查询流程

1. 获取原文词形。
2. 识别 lemma。
3. 获取当前句子。
4. 查本地缓存。
5. 缓存不完整时查询可用 Provider。
6. 合并重复义项。
7. 保留来源。
8. 根据词性和上下文排序。
9. 立即显示已有结果。
10. 后台补充缺失字段。
11. 将可缓存结果保存本地。

单个 Provider 失败不能让整个查词流程失败。

### 3.2.5 语境与短语

必须改善多义词排序、英美发音（数据可用时）、动词词形还原、常见短语识别、可变形短语识别、词性区分、例句和同义词辨析。

例如：take/took/taken、look into、carry out、take into account、play a role in。

不能只做原文字符串精确匹配。

没有可靠义项时，诚实显示缺少结果；不允许编造词典定义。

### 3.2.6 缓存与离线

- 本地优先。
- 缓存按 provider 和版本管理。
- 旧缓存可刷新。
- 缓存失败不删除用户词条。
- 离线时已有词典结果仍可用。
- 生词本、笔记、复习状态与词典缓存分开。

### 3.2.7 验收

- 至少两个真实词典来源查询成功。
- 同一单词可以合并多个词典结果。
- 词性、英文释义、中文义项和来源显示正确。
- 多义词上下文排序有测试。
- 词典失败时仍显示本地已有结果。
- 缓存重启恢复。
- 没有 API key 泄漏。

## 功能三：真正可视化的连线复习题（P1，用户明确要求）

### 3.3.1 当前缺陷

之前的连线题只是两个按钮点击配对，没有任何连接线。这次必须实现真正的视觉连线。

### 3.3.2 交互要求

界面左右两列：

- 左侧英文词/短语。
- 右侧中文释义。
- 两列随机排列，不能依赖固定位置猜答案。

流程：

1. 点击左侧英文，显示清晰选中态。
2. 点击右侧中文。
3. 系统验证配对。
4. 正确时在两个选项之间绘制可见连接线。
5. 两个选项同时标记完成并禁用。
6. 错误时显示明显反馈，可短暂显示错误连接/抖动，再允许重试。
7. 已使用的中文选项不能再匹配其他英文。
8. 全部配对后进入下一题或完成阶段。

### 3.3.3 绘线技术

使用 SwiftUI 原生能力，不需要第三方绘图 UI 框架。

可采用：

- GeometryReader 获取整体容器尺寸。
- AnchorPreference / PreferenceKey 记录每个选项的中心点。
- 统一 coordinateSpace 计算左右端点。
- Canvas 或 Shape/Path 绘制 Bezier 曲线。
- 连接线层放在选项合适的视觉层级。
- 连接线设置 allowsHitTesting(false)，不阻断按钮点击。
- 滚动、动态字体、设备旋转、布局变化时重新计算端点。
- 正确连接线保留至本题结束。
- 选项位置变化时连接线同步更新。
- 选择/正确/错误/完成状态不能只依赖颜色，还要使用边框、符号、文案或线型。

连接关系至少保存 questionID、leftOptionID、rightOptionID、state。实际答案正确性仍由 Domain/Service 判断，View 不能自行决定正确答案。

### 3.3.4 已完成项不可重复选择

修复上一轮 S13/S14：

- 已配对英文禁用。
- 已配对中文禁用。
- UI 禁用只是第一层。
- Repository/Service 必须再次校验选项是否已经被使用。
- 快速双击、重复提交和 VoiceOver 操作不能重复消费选项。
- 错误尝试次数不能被无意义点击污染。

### 3.3.5 无障碍

VoiceOver 必须能表达英文选项、当前选择状态、中文候选、已完成匹配、错误匹配和当前题目进度。

对无法直接感知曲线的 VoiceOver 用户，提供等价的顺序选择体验，不能让视觉连线成为唯一交互方式。

### 3.3.6 验收

必须有真实截图：

- 初始未选择。
- 选择英文。
- 错误匹配。
- 正确连线。
- 多条连接线同时存在。
- 已完成两端禁用。
- 最后一组完成。
- 旋转/滚动后连线仍正确。
